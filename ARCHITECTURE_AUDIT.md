# Architecture and D1 Audit

**Reviewed:** 2026-11-08
**Scope:** repository code/configuration, local Wrangler D1 snapshots, local application logs, and read-only Cloudflare D1 metadata available to the configured account. No production records were queried or changed.

## Initial findings

### D1 schema and data consistency

- The initial 70-table development snapshot differed from the manifest in four places: `ActionPlanItem` had 0 rather than 3 rows, `ActionPlanItemDetails` had 0 rather than 3, `Module2EAuctionPlanningAssumption` had 0 rather than 4, and `User` had 4 rather than 5. After the complete seed, all 70 application-table counts match the manifest exactly (162,805 rows total). The dev database has 71 physical tables because it also contains the internal seed checksum ledger, which has 10 rows. The expanded dev checks report no foreign-key violations, tenant-reference orphans across all 21 tenant-scoped tables without native `TenantMaster` foreign keys, checked transaction-to-assessment or assessment-to-customer orphans, or duplicate transaction source keys.
- A second, older local Wrangler snapshot has 38 tables and about 98,604 rows. It lacks tables and seeded data present in the current 70-table snapshot. Standard seed, drift, and Worker dev commands now pin Wrangler local persistence to `backend/.wrangler/state`; the old snapshot is left intact but is no longer selected by those commands.
- The transaction natural key now has a partial unique index for complete source keys in both local and remote development D1. The checked dev data has no duplicates; production has not been audited because its D1 database is unavailable in the configured account.
- The assessment workbook upload path used `AssessmentRecord.customer_id` as the transaction and R2 metadata `tenant_id`, even though `AssessmentRecord.tenant_id` is the security boundary. Its validation query also read by record ID alone, and failed-upload cleanup deleted matching source IDs across tenants. Upload, validation, assessment updates, object metadata, and rollback now use the assigned tenant, with cleanup additionally scoped to the assessment. The orchestration adapter also now passes the resolved tenant into upload and reanalysis calls. Regression tests cover foreign-tenant rejection, successful row ownership, partial-import cleanup with colliding IDs, and corrected-dataset reprocessing. Read-only checks in current local development D1 found zero existing transaction, validation, or object metadata tenant mismatches for assessment uploads.
- User registration, login, and admin provisioning resolve email case-insensitively, while SQLite's original `UNIQUE(email)` constraint was case-sensitive. Local D1 and remote `consulting_dev` currently have zero case-folded duplicate email groups. Registration now uses a functional unique index on `lower(email)`, an insert conflict guard, and a migration preflight that refuses to continue if existing duplicate identities need a human decision. Production must pass the same duplicate preflight before this index is applied there.
- The selected ownership model is one tenant per user, stored in `User.tenant_id`. Authentication resolves tenant scope from that persisted assignment; request-supplied tenant IDs are only accepted when they match it. Pending users may remain unassigned, but D1 prevents active customer users without a tenant. A read-only remote development check found zero active unassigned users. The canonical schema also guards the 21 tenant-scoped tables without native tenant foreign keys against unknown tenant IDs, makes tenant IDs immutable, and requires soft deletion for tenant records.
- The user table also had both a case-sensitive unique index and a redundant explicit plain email index. The migration removes the explicit index; new databases use only the functional case-insensitive unique index. Existing databases retain SQLite's internal index from the old inline constraint because removing it would require rebuilding the table and its foreign-key relationships.
- Five tenant-scoped aggregate tables (`VendorPriceRank`, `ConversionFunnelPhase`, `DatasetMetricSummary`, `Module1MonthlySpend`, and `Module1CurrencyBreakdown`) used global primary keys on vendor, phase, metric, month, or currency. This blocked valid same-key rows for separate tenants and could make seed/retry writes silently ignore another tenant's data. The compatibility migration now rebuilds them with `(tenant_id, natural_key)` primary keys while copying rows, and removes four now-redundant key indexes. Local migration tests verify row preservation, cross-tenant key reuse, and idempotence; the drift gate checks primary-key column order.
- `d1-schema.sql` and `d1-reference-schema.sql` previously repeated 21 table and index definitions. The duplicate definitions have been removed; `d1-schema.sql` is canonical, the old reference path is a comment-only compatibility placeholder, and deployment no longer issues a second DDL call.
- The global category summary totals do not reconcile to the transaction ledger totals when grouped without matching assessment, period, and inclusion filters. This is not enough evidence to call the figures corrupt; each dashboard/report needs a documented source scope and reconciliation rule.
- The seed documentation described the complete manifest import, but `db:seed:d1` only imported the base seed. A fresh or partially seeded database could therefore appear functional while missing reference and feature data.

### Cloudflare D1 utilization

- Read-only metadata for `consulting_dev` now shows 71 tables and **326,045,696 bytes** (about **311 MiB**, or 62% of the 500 MiB per-database cap). The normalized email index, tenant guard triggers, and tenant-composite aggregate keys are present; the old internal index from the former inline `UNIQUE(email)` remains. The configured production database, `consulting-db`, could not be found in the currently authenticated Cloudflare account (Wrangler error 7404). A fresh read-only `wrangler d1 list --json` on 2026-11-05 also found no entry matching configured production ID `9286122b-f5e3-413a-9061-a36a84a8787a`; this may be an account/configuration mismatch and is not evidence that the database is absent from every Cloudflare account.
- Seven-day query insights included a `ProcurementTransaction` count scan averaging 95,416 rows read, and an aggregate scan averaging 190,836 rows read with about 2.6 seconds average duration. The latest planned remote drift audit reported 545,780 rows read across table counts and relationship checks, including all 21 tenant-reference and five tenant-primary-key checks. Cloudflare did not attribute the earlier aggregate to a route; treat it as audit-driven until request-level production evidence says otherwise. Run remote deep drift checks only during planned audits, not on request paths or every deployment.
- The duplicate-transaction diagnostic now filters to complete natural keys before grouping, matching the partial unique index predicate. Local and remote read-only `EXPLAIN QUERY PLAN` checks show it scans the covering `idx_procurement_tx_source_row_unique` index without a temporary `GROUP BY` B-tree; the regression test proves incomplete rows are excluded and the covering-index plan is retained. This reduces table lookups and grouping work, but the diagnostic still scans all complete source keys, so it remains a scheduled audit query rather than a request-path check.
- Read-only SQLite plans against the current local D1 snapshot show per-assessment transaction statistics use `idx_procurement_tx_assessment_version_category`; the global Executive Brief rollup searches by tenant through `idx_procurement_tx_po`; and the DB status count uses the covering `idx_procurement_tx_tenant` index. The two aggregate queries still build temporary B-trees for `COUNT(DISTINCT ...)`, and a full count still visits every tenant-index entry. The assessment query already has an applicable index despite its stale “no index yet” comment; no wide index was added without evidence that its extra storage/write cost would repay the remaining work.
- Batched the compatibility migration path: one catalog query now inventories required tables, columns, and indexes; duplicate-email preflight remains read-only; needed compatibility changes are emitted as one idempotent SQL-file invocation. The local schema sync now rebuilds the five tenant-key tables in one compatibility invocation and applies 199 canonical schema statements; subsequent compatibility runs perform one metadata query and no writes. Locally, Wrangler passes SQL files through Miniflare's D1 `batch()`; remotely, Wrangler uses the D1 import/upload/poll workflow, so one Wrangler invocation must not be described as one network request. Before batching, the per-table probes and index checks would issue about 41 Wrangler invocations on this already-migrated schema. Regression tests cover first-time migration, duplicate identity refusal before writes, index validation, composite-key rebuilds, and idempotent reruns.
- Reference data caching was keyed by the request's telemetry proxy, which is recreated for every Worker request; the configured cache therefore missed across requests despite a 60-second TTL. Telemetry wrappers now carry a stable identity for their underlying D1 binding, and cache reads plus write invalidation use that identity. A regression test proves two separately instrumented requests share a cached reference result and that invalidation through either wrapper clears it.
- The separate Module 2 derived-analysis cache had the same request-proxy keying defect, so repeat dashboard/category requests re-read and re-analyzed the same assessment transactions. It now keys by the underlying D1 binding, reports hit/miss metrics, removes expired entries, bounds each binding to eight LRU analyses and 30,000 transaction rows, and shares in-flight loads. A single analysis above the row budget is returned but not retained. Workbook ingestion invalidates after each successful D1 batch; upload rollback, document deletion, tenant reset, assessment-version rollback, and existing material/assumption mutations also invalidate affected tenant data. Regression coverage verifies reuse across separately instrumented requests, targeted invalidation, expiry, capacity/row eviction, oversized-result handling, and in-flight invalidation. This prevents a partially ingested analysis from remaining cached after the final batch or rollback while constraining per-isolate cache growth.
- Module 2 routes previously read `AssessmentRecord` once to validate tenant ownership and again to fetch `customer_name`. The ownership query now selects both fields with the same `assessment_id` and `tenant_id` predicate, and customer-facing handlers use that trusted result. A regression test verifies the response name and exactly one assessment-table read.
- The admin D1 schema endpoint previously issued one table-inventory query plus one `pragma_table_info` query per table (about 71 D1 statements for the current schema). It now joins `sqlite_master` with SQLite's table-valued `pragma_table_info` and groups the returned rows in memory, reducing schema inspection to one D1 statement; a route regression test verifies the single schema query, and the combined SQL was exercised against local dev D1.
- The ingestion read previously fetched the entire tenant document queue and only the newest 500 validation records, while calculating its summary from that truncated page. The API now keyset-pages both streams in 100-row batches, orders by stable timestamp/ID pairs, and uses tenant-scoped indexes; the profile and validation screens expose load-more controls, and direct links fetch the requested tenant document by ID. A single aggregate computes total counts and validation metrics over the full tenant dataset on initial reads; continuation requests skip that full-table summary scan. The summary now reflects the complete dataset instead of the first 500 rows. Tests cover 205 validation rows, multiple tied timestamps, tenant-scoped cursors, page boundaries, complete totals, and direct document lookup.
- GraphQL ingestion queue and validation fields now return bounded connection pages with validated `first` and opaque keyset cursors, `hasNextPage` and `endCursor` metadata, and cursor checks tied to both the current tenant and stream. The composite dashboard returns bounded first pages; the root fields support continuation requests. Invalid arguments and cursors produce request-correlated warning logs. Tests cover tied timestamps, continuation, invalid sizes/cursors, cross-stream and cross-tenant cursor rejection, and the HTTP GraphQL contract.
- Most D1 routes also issued a standalone `SELECT 1` readiness query immediately before their real database operation, and the top-level tenant middleware already performs an authenticated D1 read. Binding checks now validate that a D1 binding exists without another round trip; the explicit assessment system-info health route retains its live probe, and unsupported Module 2 paths now return without a database query. A tenant-read regression test confirms request query count dropped from two to one. GraphQL missing-binding failures are consistently returned as 503 instead of depending on the removed readiness probe.
- D1 runtime metrics previously returned hard-coded zero values, and cache reads were absent from query telemetry. The Worker now aggregates query counts, failures, slow queries, execution time, rows read/written, and reference-cache hits/misses/coalesced reads per D1 binding and isolate. The admin-only `/api/db/metrics` route and admin GraphQL `queryMetrics` field expose live values and request-correlated recent query audits, including database and wall-clock duration provenance plus batch timing; customer dashboard responses omit the global metrics field. Each isolate retains only the newest 100 audit rows. These in-memory totals reset when an isolate restarts and are not a durable or cross-isolate analytics store.
- D1 batch telemetry previously added the whole batch wall time once per statement, overstating request and runtime duration for multi-statement writes. Metrics now use Cloudflare's per-statement duration when available, mark equally apportioned batch wall time as an estimate when it is not, retain total batch wall time on each audit row, and issue one batch-level latency warning if the batch is slow without an individually slow statement. Regression coverage verifies non-duplicated totals, duration provenance, and batch warning behavior.
- Cloudflare's Free D1 limits include 500 MB per database, 5 million rows read/day, and 100,000 rows written/day. The development database is about 62% of the single-database size cap, although current daily query volume is zero. The index build's one-time D1 metadata reported 161,092 rows read and 63,746 rows written; row scans and index builds should be planned against the daily quota. See [D1 pricing](https://developers.cloudflare.com/d1/platform/pricing/), [D1 limits](https://developers.cloudflare.com/d1/platform/limits/), and [D1 metrics](https://developers.cloudflare.com/d1/observability/metrics-analytics/).

### Logging and failure visibility

- Local log files contained 438 distinct structured entries through 2026-10-30: 200 info, 57 warn, 180 debug, and one error. The one error had no stack or request ID. These files are local/stale evidence and do not establish current production log volume.
- The Worker top-level exception handler returned errors without logging the exception or attaching a correlation header. GraphQL field and validation errors were returned inside execution results without being logged; the route now emits request-correlated warnings for rejected operations and error logs with resolver stacks and field paths. Malformed JSON was silently converted to `{}`. The Worker D1 proxy now instruments direct `prepare().first/all/run()` calls and batches, records Cloudflare's `rows_read`, `rows_written`, and database duration metadata, and emits request summaries including cache activity. Durable log export and alerting still require account-level configuration.
- The backend Wrangler config now explicitly enables Worker logs, invocation logs, persistent log delivery, and a 100% head-sampling rate in the shared config inherited by dev and production. This closes the configuration gap; actual retention, export destination, and alert delivery are still account/platform concerns and have not been verified for production. The application logger's local filesystem persistence is best-effort and is not a durable Cloudflare Worker log store; platform Workers Logs are the production source.
- The shared backend logger also enabled filesystem persistence by default outside `NODE_ENV=production`; in Workers this used a memory-backed virtual filesystem, and directory/write exceptions were swallowed. Worker environments now disable that non-durable write path and use the already-persisted structured console stream. When file persistence is enabled in local Node runs, logger-internal directory/write failures now emit structured error records with stacks to console and the in-memory history while preserving application flow.
- Two ingestion response paths silently converted malformed stored currency JSON into an empty list. They now share a parser that preserves the fallback while logging the parse error stack, authenticated tenant, document ID, fallback action, and request ID.
- Browser errors previously had no central forwarding path. A bounded telemetry endpoint and root React error boundary now report uncaught errors, rejected promises, render failures, and caught warning exceptions with scrubbed messages/stacks and correlation IDs. Routine warnings are not uploaded. The endpoint does not touch D1. Cloudflare-side alerting, durable log export, and an edge rate-limit rule still need account-level configuration.

### Security claims and encryption boundary

- The database schema screen and security copy previously claimed SOC 2 / ISO certifications, end-to-end AES-GCM protection for every financial record, TLS 1.3, sub-800ms performance over multi-million-row datasets, 2GB ETL under 15 minutes, 99.95% availability, multi-region failover, and instant recovery. The header also displayed an unverified sub-800ms SLA and a completed Module 1 run was labeled 100% real-time processing. Those guarantees were not established by repository configuration or telemetry. The UI now describes configured D1/R2 at-rest encryption, application TLS, generated artifact encryption, measured query instrumentation, and recovery settings that still require Cloudflare-account verification. Cloudflare documents AES-256 encryption at rest for D1/R2 and TLS for service/API traffic ([D1 security](https://developers.cloudflare.com/d1/reference/data-security/), [R2 security](https://developers.cloudflare.com/r2/reference/data-security/)).
- The unused frontend crypto helper silently selected a fixed development key compiled into client code. That fallback is removed; the helper now requires an explicit caller-managed key and validates key length, algorithm, operation usage, IV/tag shape, and ciphertext encoding. Decryption failures include the underlying error stack in structured logs. The helper has no production call sites, so it does not imply field-level encryption of D1 transaction columns.

### Intermittent behavior

- A `main` push could run both the development deployment workflow and a second workflow that deployed the base Workers, creating competing deployment outcomes.
- Development frontend builds and Wrangler dev sessions pointed to the production backend Worker; the backend dev environment also advertised the production frontend URL. Standard scripts now select the `dev` environment and pin a single local D1 state directory.
- The default seed command imported only a subset of the manifest while the manual deployment seed imported all files. The default now imports the complete manifest, records checksums for the base and feature seeds, and skips unchanged files on repeat runs.
- These concrete configuration/data-path conflicts explain reproducible classes of “works once, fails next time” behavior. They do not explain every intermittent issue; request-specific production logs and route-level telemetry will be needed for that.
- The Module 2 strategic sourcing overview also lacked an in-flight request sequence guard. A slow prior-assessment response could overwrite a newer assessment, while a failed `null` fallback could leave the prior summary in view. The workspace now invalidates superseded requests and clears the previous assessment's state on selection changes; deferred-response tests cover both cases.
- Module 2 dashboard and category API wrappers also converted HTTP/network failures into `null` or empty arrays, so a failed API could look like a valid no-data result. Those two wrappers now preserve failure status and Worker request ID; the workspace shows actionable failure guidance, logs assessment/feature/status/correlation context, keeps any successful partial dataset, and clears the alert after a successful retry.
- Several Module 2 analysis views launched new assessment/filter reads without invalidating older requests. A slow response from a prior assessment or filter could replace the current result or error. A shared latest-request sequence now guards Volume Aggregation, Category Specialisation, Payment Terms, Consolidated Savings, Specification Rationalisation, and Alternate Sourcing; Vendor Consolidation has the same protection. These readers clear the previous dataset during reload, check request currency after parsing the response body, and ignore stale failures as well as successes.

## Changes made in this pass

- Added validated request correlation IDs, returned them in `x-request-id` on every Worker response, logged 4xx/5xx responses with method/path/status/duration, and logged caught Worker and GraphQL exceptions with stacks and correlation IDs.
- Added GraphQL execution-result diagnostics: validation and operation rejection logs include the request ID, operation name, error message and location; resolver errors include their field path and underlying exception stack.

- Malformed or non-object JSON now fails fast with a structured 400 response; logs include method, path, request ID, and the underlying parse exception. Empty bodies remain supported where the route permits them.
- All Worker JSON request parsing now uses a streaming byte-bounded reader: 1 MiB by default, with an upload envelope sized for 10 MiB source files. It checks declared and streamed byte counts, returns correlated 413s for oversized bodies, and logs unexpected stream failures with stacks. Ingestion validates Base64 size and structure, and the frontend rejects files above the same 10 MiB limit before reading them. Route-level `request.json()`/`request.text()` parser bypasses were removed.
- Structured PCBI evidence parser failures no longer disappear inside an empty-row fallback.
